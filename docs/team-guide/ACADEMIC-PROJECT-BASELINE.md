# RAWAQA كأساس لمشروع تخرج BIS

هذا الملف نقطة بداية أكاديمية، وليس موافقة من الكلية أو الدكتور. يجب اعتماد نطاق المشروع ومتطلبات التقرير قبل تقديمه رسميًا.

## 1. عنوان مقترح

**RAWAQA: An Integrated E-Commerce and Business Operations Information System**

بالعربية: **رواقة: نظام معلومات متكامل لإدارة التجارة الإلكترونية والعمليات التجارية**.

## 2. لماذا يناسب BIS؟

لأن المشروع يجمع بين:
- نشاط تجاري واضح ومشكلة تشغيلية.
- تحليل عمليات البيع والشراء والمخزون.
- إدارة بيانات العملاء والمنتجات والطلبات.
- تصميم نظام معلومات يربط العمليات.
- ضوابط وصلاحيات وأمن معلومات.
- إمكانية استخراج تقارير ومؤشرات تساعد الإدارة.

لا ينبغي تقييمه بعدد التقنيات فقط؛ القيمة الأكاديمية هي تحليل المشكلة، تصميم الحل، وتقييم أثره على العملية التجارية.

## 3. المشكلة (صياغة أولية)

تحتاج أنشطة التجارة الإلكترونية إلى تنسيق موثوق بين عرض المنتجات، استقبال الطلبات، إدارة المخزون، متابعة المدفوعات، وتنفيذ الطلبات. يؤدي تشتت هذه العمليات أو الاعتماد على إجراءات يدوية إلى أخطاء تشغيلية، تكرار بيانات، ضعف المتابعة، وصعوبة تكوين صورة موحدة للإدارة.

يقترح المشروع دراسة وتصميم وتقييم نظام معلومات يربط هذه العمليات في منصة واحدة.

## 4. الأهداف

1. توثيق دورة العمل من عرض المنتج حتى إتمام الطلب.
2. تحديد المستخدمين واحتياجات كل منهم.
3. تنظيم البيانات والعلاقات بين العملاء والمنتجات والطلبات والمدفوعات والمخزون.
4. تطبيق ضوابط تحقق وصلاحيات مناسبة.
5. توفير واجهة للعميل ووظائف إدارية للموظفين.
6. اختبار السيناريوهات الأساسية والاستثنائية.
7. اقتراح تقارير إدارية قابلة للقياس بناءً على البيانات المتاحة.

## 5. النطاق الحالي

يشمل النظام الحالي وظائف متجر إلكتروني وإدارة تشغيلية مثل المنتجات والتصنيفات والسلة والطلبات والمخزون والكوبونات والعملاء والمحتوى وبعض وظائف الدفع والتكامل.

أما BI متقدم أو DSS أو توقع المبيعات أو ERP كامل، فهي إضافات مقترحة وليست ضمن الوظائف التي ينبغي نسبتها للنسخة الحالية دون تنفيذ.

## 6. مخرجات التحليل والتصميم المقترحة

- Project Charter وScope Statement.
- Problem Statement وObjectives.
- Stakeholder Analysis.
- As-Is / To-Be Business Process.
- Functional Requirements وNon-Functional Requirements.
- Use Case Diagram.
- Context Diagram وDFD Level 0/1.
- ERD وData Dictionary.
- Activity Diagram لعملية Checkout.
- Sequence Diagram لإنشاء الطلب والدفع.
- Architecture Diagram.
- Security & Access Control Matrix.
- Test Plan وTest Cases ونتائج تنفيذ فعلية.
- User Manual وFinal Report وPresentation.

## 7. تقييم النظام

يجب أن يحدد الفريق مقاييس قابلة للقياس، مثل:
- نجاح إنشاء الطلب في السيناريو الصحيح.
- منع طلب كمية غير متاحة.
- منع تكرار إنشاء الطلب عند إعادة إرسال نفس الطلب.
- منع العميل من رؤية طلب أو مدفوعات عميل آخر.
- دقة الإجمالي وفق قواعد معتمدة.
- سهولة إتمام مهمة شراء تجريبية.
- وضوح لوحة الإدارة للمستخدمين.

لا تضع نسب نجاح أو أرقامًا قبل تنفيذ الاختبار وجمع نتائجه.

## 8. أخلاقيات وملكية العمل

RAWAQA عمل تجاري حقيقي لصالح عميل/شركة، لذلك:
- يجب الحصول على موافقة صريحة لاستخدام الكود أو العلامة أو الصور في مشروع التخرج.
- لا تستخدم بيانات عملاء حقيقية في التسليم الأكاديمي.
- أنشئ نسخة منفصلة ببيانات تجريبية.
- وضّح مساهمة كل عضو بدقة.
- لا تقدّم نفسك أو أي عضو على أنه مالك النشاط ما لم يكن ذلك صحيحًا.
- احذف الأسرار ومفاتيح API وبيانات الاتصال الخاصة من المستندات والعروض.

## 9. أسئلة يجب اعتمادها مع الدكتور

1. هل يسمح باستخدام نظام قائم وتطويره أكاديميًا؟
2. هل يجب أن تكون كل أجزاء النظام من تنفيذ الفريق؟
3. ما عدد أعضاء الفريق المعتمد؟
4. ما المستندات والرسومات المطلوبة؟
5. هل يلزم تطبيق BI أو Data Mining أو AI؟
6. ما شكل التقييم والاختبار المطلوب؟
7. هل هناك قالب رسمي للتقرير؟
8. هل يلزم خطاب موافقة من الجهة المالكة للمشروع؟
